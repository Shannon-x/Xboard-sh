## 客户端能力约定

`include_customization=1` 只表示认识三项资源，不能代表认识增值组。

支持增值组的主题需要给以下 GET 请求增加 `include_addon_groups=1`：

- `/guest/plan/fetch`
- `/user/plan/fetch`，包括指定 `id` 的请求
- `/user/info`
- `/user/getSubscribe`

未声明的旧客户端继续获得兼容视图。已购增值组的用户用旧界面续费不会被静默降配：
省略 `addon_groups` 沿用已购组；只有显式 `[]` 表示移除可选组。
`granted_groups` 即使由客户端回传也不是授权依据，必须重新计算。

主题补丁仅针对已实现增值组 UI 的 `dev`；不要向只支持三项资源的旧主题虚报该能力。
旧后端会忽略新增 GET 参数；新后端也必须继续支持旧参数缺席。

## 生产升级顺序

1. 记录前端、中间件、Web/队列/节点同步容器的确切版本和镜像 digest，备份数据库、挂载配置、插件；验证备份可恢复。不要只记 `latest`。
2. 用脱敏数据在预发布环境先演练；先保留旧前端，确保新后端兼容它。需要报价功能时先准备含两个 quote 映射的中间件。保留原加密密钥与旧路径映射。
3. 使用经过门禁的目标镜像执行迁移。新增列虽然对旧代码通常兼容，DDL 仍可能等待锁，须安排维护窗口并控制写入；先确保已有支付/队列任务状态可追踪。
4. 执行 `php artisan xboard:check-upgrade`。这是只读检查，失败不应继续切换。仅重建镜像不会自动运行迁移。
5. 将 Web、Horizon/队列及其他加载后端代码的常驻进程切到同一 digest，避免新 Web 写入快照却被旧 worker 按固定套餐开通。升级时不要清空付款队列。
6. 验证旧前端：公开配置、套餐列表、登录、当前订阅、固定套餐购买、续费、取消和真实支付回调/开通；再启用新主题与自选套餐。单独确认语言 JSON 和图片没有被挑战页替换。
7. 小流量验证后再扩大发布。出现新增 5xx、接口结构异常、队列失败或付款与权益不符，应停止切换并按下述边界处理。

已有 `xboard:update` 除迁移外还会安装插件、重算重置时间、刷新主题并终止 Horizon。
不要把它当成纯只读检查；这次没有执行生产更新命令。

## 回退边界

运行 `php artisan xboard:check-upgrade --require-legacy-rollback` 可以拒绝已有自选配置、订单快照或用户权益时的旧镜像回退；这是保守检查，不保证所有外部插件都可回退。

- 尚未写入新功能数据：可以在演练通过后考虑同时回退 Web/worker 镜像，通常保留新增可空列，不做数据库 rollback。
- 已有自选订单或权益：不能仅换回旧镜像。旧代码会忽略快照和增值权益，可能按错误规格开通或漏下发用户。优先前向修复；确需回退必须协调停写、待付款订单/回调/队列，并制定经过验证的数据转换或恢复方案。
- 不要为了回退镜像运行 `migrate:rollback` 或 `xboard:rollback`。它们可能删除快照/权益列；恢复旧备份也会丢失备份之后的新订单，必须先做账务核对。

## 后续变更规则

新增字段不等于自动兼容；尤其禁止未经能力协商向旧客户端遍历的对象中加入新语义键。
更改返回类型、可空性、金额单位、周期名、序列化 Job、权限来源或队列职责，都必须补旧请求/旧数据测试。
跨项目新增 API 必须同时核对中间件路径映射，按“后端兼容旧前端，中间件先支持新路径，最后开新功能”的顺序发布。
每次升级仍需按风险验收；本次门禁覆盖已知契约，不能保证任何未来提交都不会产生其他问题。
